## Accepted decisions

- **D-01 — Sensitive public lists need separate permission.** The owner approved a separate, remembered permission for public mutes and categorized lists. Ordinary identity access covers profile, relay preferences and follows. Bind the sensitive-list allowance to the selected user and verified napplet publisher/app; provide trusted revocation. Existing identity grants do not imply this new allowance. Encrypted list contents remain excluded.

Basis: public lists can reveal interests and exclusions, and NAP-IDENTITY permits restrictions on sensitive lists. Tradeoff: another permission decision. This governs shell-mediated identity replies, not the confidentiality of data already published to public relays. A separate relay capability can expose public events under its own existing rules.

- **D-02 — Existing scope and authority remain in force.** Read only the identity captured by native registration. No guest-selected owner, private key, signing or decryption. Revoke pending delivery on background, close/replacement and identity changes. Value/zaps remain Phase 4. Continue one phase at a time until Phase 2 completes or weekly usage reaches 50% consumed; latest live check 20%.

- **D-03 — Preserve offline reads with older cache.** The owner selected option 2: if identity data is over five minutes old and a relay refresh is unavailable, return the existing older cached data. Use a recent cache for five minutes; attempt a bounded refresh once older. With no cached result, return the canonical error rather than inventing data. Cached events must remain validated, account-bound and subject to current permission/lifetime checks.

Basis: retain useful offline behavior. Tradeoff accepted by the owner: the identity API has no freshness field, so a napplet can treat older follows, mutes or other public identity data as current. Do not add a nonstandard freshness field or silently convert missing cache into a successful empty result. Concrete storage, retention bounds and cancellation remain engineering choices to verify.

- **D-04 — Select three global public list categories.** The owner chose option 1: `bookmarks` maps to NIP-51 kind 10003 (`e` and `a` values), `pins` maps to kind 10001 (`e` values), and `interests` maps to kind 10015 (`t` and `a` values). Read only the selected user's public event tags. Return an explicit canonical error for other list types. Named collections and additional categories remain recorded gaps, without a promised delivery phase.

Basis: these three names match the identity draft's examples and have defined NIP-51 global formats. The draft's generic wording describes parameterized events, which conflicts with those examples' current standard global kinds; document this selected mapping rather than imply an unqualified draft mandate. Named collections need additional selection rules. Returning a public address reference in a global list does not authorize fetching or expanding the referenced collection.

- **D-05 — Return accepted public profile badges.** The owner selected option 1: return only badges accepted for public display, verifying the selected user's profile list and each referenced award/definition. Do not infer acceptance merely from an issuer awarding a badge. Preserve the user's order and validate issuer, definition address and recipient. Missing or invalid references must not become invented awards.

Basis: anyone can award badges without recipient consent; NIP-58 provides the recipient's public acceptance/display list. Tradeoff: unaccepted awards are excluded from this selected identity profile even though the generic draft describes awarded badges. Record this explicit selection. A future interface for all awarded badges is a separate gap.

### Engineering discretion

No planned product questions remain. Select declared finite request/cache/join limits, exact storage/consent composition and portable test commands within D-01–D-05. Blocks have no selected public backing format: preserve canonical unsupported empty output and record the gap; never reinterpret mutes as blocks. Keep zap reads empty under the accepted Phase 4 deferral. Existing trusted relay destinations remain authoritative; discovered NIP-65 metadata and event relay hints do not add network destinations. Extend State Lab and Feed Lab through the genuine SDK, use existing native transport/lifetime checks and verify both actual hosts. Work inline under the Codex adapter; no source push or sub-agent delegation.
