# Phase 2.4 — Upload research

**Date:** 2026-10-01
**Execution:** Inline installed-Codex fallback; no independent typed-agent guarantees.

## Selected owning profile

[CITED: pinned NAP-UPLOAD in 02.4-CONTEXT.md] Implement `upload.info`, `upload.upload`, `upload.status` and `upload.status.changed`. Public data is Blob/ArrayBuffer; structured clone remains the guest boundary. IDs correlate requests/results; upload IDs are generated and scoped by the shell. The draft specifies cancelled state but no guest cancel method. Trusted shell Cancel and lifetime revocation supply cancellation; do not add a public method. `info` remains advisory, never a prerequisite.

[CITED: Blossom b5bd280 BUD-02/BUD-11] Use raw `PUT /upload`, not server-transforming `/media`. Signed kind 24242 contains `t=upload`, one `x` hash, one lowercase `server` domain, bounded expiration and human-readable content. Authorization is base64url without padding. Blob descriptor fields are `url`, `sha256`, `size`, `type`, `uploaded`; raw server bytes must not change. Check receipt hash and size against the approved body, then independently retrieve expected bytes before acceptance. Support existing/new blobs without silently dispatching twice. Provider diagnostics are text, not control instructions.

No body was uploaded. Select `https://blossom.nostr.build` as the editable default on this observed eligibility and its documented policies; actual PUT/receipt behavior remains unverified.

[CITED: https://blossom.nostr.build/] Free uploads are media-only up to 20 MiB; PDF/SVG/ZIP require a plan. The raw endpoint rejects GPS-bearing media rather than stripping it. Document provider constraints; shell photos are sanitized before review; attachments retain bytes and may be rejected by provider policy. An editable server permits a separately configured provider. Do not hide these constraints, automate a payment or infer reliability/retention from an eligibility check.

## Declared engineering limits

[SELECTED ENGINEERING PROFILE] Initially 10 MiB per file to align independently retrieved receipt verification with the accepted resource bound; 256 KiB carrier chunks; one active transfer per requesting realm, two per process; eight queued reviews; 60-second total upload deadline; 120-second auth expiry; 128-byte request ID; 128 retained statuses per realm while loaded. MIME policy includes bounded supported images/audio/video and ordinary attachments, rejects active HTML/SVG/XML rendering and arbitrary executable previews. Server policy can be narrower. These are phase limits, not an approved universal large-file prohibition. Streaming/large files remain a separate open product gap.

[SELECTED ENGINEERING PROFILE] Public HTTPS DNS names only; native fresh public-address validation, pinned TLS, bounded framing and no upload redirects. Redirects could move identity-bearing authorization/bytes off the approved destination. Settings edits apply to future reviews; pending destination-bound work is revoked before a changed destination can be approved. Retain no restart-resumable raw bodies; no automatic retry.

## Architecture and patterns

Add an explicit upload-purpose snapshot/native authority rather than widening relay authority to generic HTTPS signing. Protected signing still needs the selected identity, native authority and independent signature validation; the guest receives no signed credential.

A picker handoff is local disclosure, separate from upload consent.

[CITED: developer.android.com/training/data-storage/shared/photo-picker; developer.android.com/training/data-storage/shared/documents-files] Android system selection grants selected items; use available Photo Picker with document fallback, and no broad storage permissions. [CITED: developer.apple.com/documentation/photokit/selecting-photos-and-videos-in-ios] iOS system selection is the corresponding platform surface; exact callback/entitlement/build behavior remains native engineering research, not verified by this documentation page.

[SELECTED ENGINEERING PROFILE] Sanitize photo containers before handing selected photo bytes to the guest and again before upload approval for arbitrary guest-supplied photos. Preserve display orientation/color and decoded content; do not silently resize. Start real tracer with a known PNG, then cover JPEG/PNG/WebP/GIF and normal device HEIC selection. If a conversion is required, display the resulting format/size/preview before approval; never claim byte identity to the original. Reject photos when metadata removal cannot be verified, rather than silently submitting originals. Do not promise documents/audio/video are metadata-free.

## Validation Architecture

Use existing Node type-strip contract tests and runtime browser verification, host Java/Swift authority checks, controlled TLS upload endpoints with independent byte observer, then installed Android/iOS apps using genuine SDK fixtures. New upload commands/fixtures must be created before invoking them. Correct/incorrect auth HEAD results are operator eligibility evidence only. Protected iOS signing still requires a physical device; public-identity Simulator fixture must not be presented as protected signing proof.

Acceptance requires real SDK-to-native PUT, trusted review/reject/cancel, independently recorded exact body/hash/receipt, provider failures/malformed receipts/lost acknowledgement, switching/background/identity/close/renderer revocation, genuine system picker selection/cancel and local disclosure boundaries, sanitized metadata probes and native preview. Separate held-dispatch doubles from real HTTP/lifecycle tests. Pin source, runtime, fixture and installed products; inspect actual screenshots/accessibility. Full numeric React Doctor and aislop must both reach 100/100 without suppression, and all lockfile audits must pass. Known Expo Doctor patch-pin mismatch remains disclosed until separately resolved.

## Risks and open engineering work

The public draft's progress/cancel/unknown-result representation needs an explicit interoperable selection without invented public fields. Select status/error spelling against SDK 0.27.2 projections before wiring it. Retained reconciliation records must be identity-bound and must not restore upload authority after background/restart. The default provider does not support free document uploads. Full published parity/physical iPhone signing remain CAP-14 boundaries; fixture success alone is not acceptance of those.


## Plan 03 recovery implementation notes

[IMPLEMENTATION DESIGN, not acceptance] Persist a bounded native write-ahead
record before a PUT can dispatch. Retain captured identity, provider, prepared
hash/size/type and original upload/caller attribution; never retain file bodies,
signing credentials or reusable approval. A crash between recording and dispatch
remains conservatively uncertain. Corrupt/unavailable storage must fail closed;
unresolved records must not be evicted to admit another transfer. This closes the
current in-memory-only outcome gap without reviving network authority on restart.

[PINNED PROTOCOL BASIS] Blossom
[BUD-01 at b5bd280](https://github.com/hzrd149/blossom/blob/b5bd2801d1763aa635fc8fea7a76597e0eb18990/buds/01.md)
provides `GET /<sha256>` and 404 for currently absent content. A fresh trusted
user-triggered read must capture the stored provider/hash, current identity and
native foreground lifetime. Verify bounded complete bytes and hash for 200;
validate complete response framing before accepting 404. A matching copy does not
prove which attempt stored it, and current absence does not promise a previous
attempt can never finish later. Redirects, authentication errors, malformed or
mismatched bodies and timeouts retain uncertainty. No automatic PUT, provider
fallback, reuse of signing credentials or remote deletion is implied.

[OBSERVED SOURCE GAP] Existing PUT readers classify rejection statuses before
validating complete body framing. Tighten that path during fault acceptance so a
truncated or ambiguously framed error response cannot settle a dispatch as a
definitive rejection. Keep this distinct from the resource and published-artifact
parser profiles. Existing native request bounds also combine pending and active
work; plan03 must explicitly implement/test its queued-review and active-transfer
limits rather than infer them from the current two-request cap.
