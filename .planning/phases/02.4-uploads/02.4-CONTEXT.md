<decisions>
## Implementation Decisions

### Rails and destination
- **D-01:** Initially support Blossom only; explicitly reject NIP-96 requests. Basis: NIP-96 is deprecated in favor of NIP-B7, BUD-02 preserves exact bytes, and one rail reduces the initial native validation surface. Tradeoff: NIP-96-only providers are unsupported; required napplets have not yet been audited for that dependency.
- **D-02:** Ship one documented upload server editable in trusted Settings. Show the selected destination in upload review and never automatically fall back to a different provider. Basis: usable first launch and predictable destination. Tradeoff: reliance on the default operator. Download defaults do not select the upload provider.

### Review and bytes
- **D-03:** Require approval for every upload. Show requesting napplet/publisher, selected identity, destination, type, size and an appropriate preview/inspection. Bind approval to the actual reviewed bytes/hash and destination. No remembered upload allowance. Basis: a durable public upload may link the file to the selected identity; tradeoff is an extra review step.
- **D-04:** Strip photo metadata before preview and approval; upload the reviewed sanitized bytes. Other attachments retain bytes with a metadata warning. Basis: reduce location/device/timestamp disclosure. Tradeoff: changed hash and lost camera information. Do not silently send unsanitized photos when sanitation fails or imply all attachment metadata is removed.
- **D-05:** Enable the system photo/file picker. Only user-selected files become readable by the requesting napplet; no whole-library access. Selection is separate from upload consent, and the napplet may read a selected file even if upload is declined. Basis: normal device attachments must work.

### Lifetime and recovery
- **D-06:** An already approved upload continues across loaded napplet switches while foregrounded. Stop on app background, requesting napplet close/replacement/renderer loss or identity change. Keep trusted progress/cancel accessible while the guest is unfocused. Reviewed bytes, identity and destination do not change.
- **D-07:** If interruption may have reached the server, disclose the uncertain outcome and check the approved destination/hash before offering a fresh user-approved retry. No automatic re-upload or provider fallback. Stopping does not promise remote deletion.

### Engineering discretion
Choose and document the concrete default provider after current primary-source research. Select exact operations, declared native/photo/type/size/concurrency/time limits and portable harness commands within these decisions. Test each authority boundary and both actual native journeys. Do not ask the owner to reapprove reversible implementation choices. Pause when weekly usage reaches 50% consumed; latest checked consumption after the authorized reset is 4%.
</decisions>

<code_context>
## Existing Code Insights

- `src/resources/resource-contract.ts` and `src/resources/resource-service.ts` establish bounded byte ownership and captured session delivery.
- `src/security/event-snapshot.ts` currently permits WSS destinations; its relay snapshot must not be reused unmodified for HTTPS upload authorization.
- `src/security/identity-vault.ts` provides protected one-use signing; native approval transport is relay-publication-specific and needs explicit upload-purpose binding.
- `src/runtime/capability-broker.ts`, `runtime/src/native-client.ts` and `runtime/src/main.ts` are the SDK/native adapter seam. Blob/ArrayBuffer must remain the guest public API; private native staging must not expose a generic file/network bridge.
- `modules/napplet-host/android/src/main/java/org/nostrocket/hypergolic/host/NappletHostView.kt` currently declines file chooser requests. Both picker paths need restricted explicit selection and captured recipient lifetime.
- Existing public DNS/TLS/framing utilities are reusable foundations; uploads need a separate PUT owner with exact approved body, response and recovery checks.
</code_context>

## Specific Ideas

The trusted shell owns destination, authorization, byte review, picker grants and progress. Public guest support must follow the selected owning draft, rather than a new guest base64 or credential API. Preserve known native runtime and source seals in acceptance evidence. Work runs inline under the installed Codex adapter; typed researcher/planner/checker guarantees are unavailable in this session.
</specifics>
