# Intent and INC decisions

The owner explicitly selected pinned NAP-INTENT/NAP-INC drafts, then chose A1/B1/C1/D1/E1/F1/G1 in the plain-text interview on3October2026. Do not reask these choices.

- D-01: Retain verified previously opened/admitted napplets as handlers in an identity-specific catalog after their views close. Trusted Settings can remove handler registration without deleting saved app data. No separate installation workflow.
- D-02: Chooser may explicitly save a default per identity/archetype; Settings changes it. Without a default choose the sole exact-compatible handler or show a chooser for ambiguity. Catalog order never selects a target.
- D-03: Every dispatch requires trusted review of native-attested requester, actual selected handler and complete bounded payload. User default does not waive approval. Explicit dTag requests use the same review; ambiguous publisher/instance dTags fail rather than route arbitrarily.
- D-04: Each loaded endpoint approves access to each exact topic for that session. Only approved subscribers receive emissions; no sender echo. Topic permission is neither durable nor implicitly granted by inc domain admission.
- D-05: Each new point-to-point channel requires approval of the two actual endpoints. Messages continue without per-message prompts until closure. No remembered pair allowance.
- D-06: Messaging continues during foreground switches between loaded napplets. Background stops topic delivery and closes channels, without deferred message queues. New channels need fresh opening/approval. Close/update/identity transition synchronously revoke endpoints and permissions.
- D-07: Reuse a matching loaded handler by default. Explicit new-instance requests need review that says another view will open. Delivery waits for actual readiness; no payload broadcast to competing handlers.

Basis: retained handlers avoid an install workflow; explicit user defaults avoid silent changes; per-dispatch review controls focus/data disclosure; topic and channel session permissions bound cross-napplet authority; foreground continuity permits cooperating views while background closure prevents hidden/deferred traffic; reuse preserves state and limits duplicate views.

Engineering bounds are implementation policy, not new product decisions: bounded JSON-only payload capture (no getters/prototypes/cycles/unsupported values), topic/id/role/convention lengths, bounded endpoint/channel/subscription/pending/result buffers, continuous native deadlines, strict source/generation/sequence checks. Unsupported wire shapes fail explicitly. Caller cannot set sender, identity, recipient generation or defaults. Domain grants disclose access to the approved same-identity handler catalog.
